# Osinara v0.14.0

Владелец может запускать безопасные автономные сценарии во внешних Telegram-группах, а память
получила явную проверяемую identity субъекта каждой записи. Одновременно обычные разговорные ответы
стали короче и отправляются как обычные Telegram-сообщения; Rich Message используется только для
реальной разметки и обязательного сворачивания длинного содержания.

## Расписания внешних групп

- Владелец управляет расписаниями внешней группы только из своего verified private Telegram-чата.
- Каждый запуск получает fresh Eve session, exact group scope и минимальный live-checked capability
  allowlist без личной или семейной памяти, credentials и trusted workspace.
- Перед запуском backend одним bounded PostgreSQL query создаёт immutable snapshot истории нужной
  группы и темы. Модель читает большие snapshots последовательными chunks через отдельный tool.
- Authorization повторно проверяется перед handoff, каждым scheduled tool call и Telegram delivery.
  Отзыв owner-role, регистрации группы или capability останавливает ещё не завершённый side effect.
- Start markers, terminal states и delivery receipts запрещают автоматический повтор после
  неоднозначного crash и не допускают двойную оплату или двойную доставку.

## Явный субъект памяти

- `remember` теперь требует один discriminated subject intent: `current_author`, `verified_ref`,
  `label` или `none`. Автор источника и субъект claim больше не смешиваются.
- `verified_ref` принимается только из profile view exact текущих Eve session, turn, conversation и
  viewer. Ref из прошлого хода или снимка другого пользователя отклоняется.
- Subject-thread требует явный `current_author` или `verified_ref` с той же identity. Нить больше не
  назначает субъект новой записи молча.
- Project-thread принимает только `subject.kind=none` и может безопасно собирать claims разных
  проверенных авторов.
- Текстовая `label` остаётся меткой claim, не становится verified profile identity и не участвует в
  subject-thread.

## Живое общение и Telegram presentation

- Постоянный prompt соразмеряет ответ с естественным ритмом текущего разговора. Для простого вопроса
  допустимы одна разговорная фраза, неполное предложение и ответ со строчной буквы без обязательного
  обзора плюсов, минусов, оговорок и встречного вопроса.
- Чистый текст детерминированно отправляется через Telegram `sendMessage` без `parse_mode` и
  `rich_message`. Поддерживаемая Markdown/HTML-разметка выбирает `sendRichMessage`.
- Ответ обязательно сворачивается после любого порога: больше семи строк, двух абзацев, шестисот
  символов или пяти пунктов; таблица и block code также считаются длинным содержанием.
- Если модель пропустила `<details>`, backend сохраняет короткий первый абзац снаружи и сворачивает
  остаток. При отсутствии безопасного короткого вступления сворачивается весь ответ.
- Plain и rich chunks проходят через общий durable final-delivery outbox; crash ambiguity не создаёт
  скрытый повтор Telegram API.

## Миграции и проверка

- `062_external_agent_schedule_scopes.sql` и `063_external_group_agent_schedules.sql` добавляют
  scoped external schedules, history snapshots и необходимые execution/delivery invariants.
- `064_turn_bound_memory_subjects.sql` связывает новые profile views с exact Eve session и turn,
  сохраняя чтение ранее созданных immutable views.
- Unit и PostgreSQL integration tests покрывают authorization races, bounded history, delivery
  ambiguity, stale/cross-viewer subject refs, multi-author project threads и выбор plain/rich
  Telegram transport.
- Production-equivalent Docker Compose gate, TypeScript typecheck, Eve build и compiled manifest
  проверяются до публикации релиза.

## Production deployment

- Production Compose graph и root-owned deployment controller не меняются.
- Release публикуется только из canonical `main` через GitHub Actions с immutable GHCR digests,
  attestations и exact release assets.
- После публикации установка требует отдельного owner approval в привязанном личном Telegram-чате.
