# Osinara v0.11.3

Исправление production startup долговременной памяти после успешной установки схемы и приложения
`v0.11.2`.

## Что исправлено

- Catch-up extraction теперь сортирует PostgreSQL `bigint sequence_id` по исходной числовой колонке,
  а не по её текстовому output alias. Диапазоны, пересекающие границу разрядности, например `9→10`
  или `99→100`, больше не превращаются в обратные и не останавливают worker с
  `AGENT_MEMORY_EXTRACTION_BATCH_INVALID`.
- Migration `057_repair_memory_extraction_sequence_ranges.sql` восстанавливает `first_sequence` и
  `last_sequence` из immutable snapshot entries. Она fail-fast останавливается, если range потерял
  snapshot source of truth, и не меняет ordinal, payload hash или provider-call audit.
- Structured-output prompt явно требует JSON-объект. Это выполняет контракт DeepSeek для
  `response_format=json_object` и устраняет definite HTTP `400` до model execution.
- Memory extraction worker публикует readiness marker только после первого успешного durable pass.
  Container health требует ещё 30 секунд стабильной работы; restart удаляет старый marker.
- Root-owned deployment validator закрепляет exact worker healthcheck и не позволит будущему release
  незаметно удалить readiness gate.

## Состояние данных

- `v0.11.2` успешно создал проверенный backup, применил migrations `049`-`056`, запустил released
  Compose graph и был атомарно promoted в production.
- Финальный post-deployment audit обнаружил restart loop нового worker. Остальные production services
  оставались healthy; worker был отдельно остановлен оператором до выпуска исправления.
- Один batch получил definite DeepSeek `400` после durable provider marker и остаётся terminal
  `failed`; автоматический или ручной скрытый retry не выполняется.
- Четыре batches, не достигшие provider call, остаются `pending`. Migration `057` исправляет их range
  metadata, после чего worker продолжит обычную очередь без повторной оплаты terminal batch.

## Установка

- Изменение exact worker healthcheck является двухфазным controller update. После canonical merge и
  до owner approval root-owned `release.sh` обновляется атомарно из точного release commit с проверкой
  SHA-256, shell syntax, ownership и mode.
- Deployment начинается только после отдельного подтверждения владельца в исходном личном
  Telegram-чате.
- Candidate images скачиваются до approval, после чего повторно проверяется backup capacity.
- Migration `057` выполняется только one-shot `migrate` service внутри released Compose graph.
- Promotion выполняется только после stabilized worker health, agent health и полного Compose wait.
