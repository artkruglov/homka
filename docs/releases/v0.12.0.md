# Osinara v0.12.0

Основной чат-агент становится единственным владельцем смысловых решений долговременной памяти.
Фоновый LLM-конвейер больше не анализирует каждое Telegram-сообщение после ответа: агент сам решает
в текущем ходе, что сохранить, нужно ли создать нить и к какой существующей нити относится запись.

## Главное изменение

- Root agent получает source-backed `remember` и принимает одно явное решение о claim и optional
  thread create/attach. Если `remember` не вызван, сообщение не создаёт никаких memory writes.
- Subagent наследует чтение и остальные trust-zone tools, но не получает descriptor `remember` и не
  может принять durable-memory решение вместо основного агента.
- `basis: agent_inferred | user_requested` различает самостоятельное решение агента и прямую просьбу
  пользователя, не подменяя подтверждение пользователя модельным выводом.
- Backend выводит author, family, group, scope и source только из verified Telegram turn и PostgreSQL.
  Модель не передаёт внутренние IDs и не может выбрать чужую trust zone.

## Atomic claim и thread write

- Claim, primary evidence, optional thread/project, thread entry, Eve session/turn provenance,
  replay metadata, embedding job и audit записываются одной PostgreSQL transaction.
- Root thread получает verified subject identity либо project identity для общей деятельности.
  Subthread наследует identity родителя; произвольная многоуровневая иерархия не допускается.
- Exact normalized duplicate усиливает существующий claim только внутри точного scope, subject и
  project identity. Одинаковый текст в разных проектах больше не может ошибочно reinforcement чужой
  записи.
- Replay thread create возвращает прежний opaque результат без повторного E5-вызова, но обязательно
  повторно проверяет актуальную membership или group registration.
- Creation notice создаётся атомарно вместе с новой нитью и сохраняет existing exactly-once delivery
  contract.

## Защита от похожих нитей

- Перед новым thread insert backend под transaction advisory lock ищет до трёх active candidates на
  том же subject/parent axis либо среди project roots текущего authorized scope partition.
- Сильное совпадение E5 title embedding (`>= 0.78`) или conservative purpose trigram similarity
  (`>= 0.9`) останавливает создание с `AGENT_MEMORY_THREAD_CANDIDATE_EXISTS` и opaque `threadRef`.
- При таком результате новый claim и временно созданный project полностью откатываются. Агент
  сопоставляет кандидатов и повторяет `remember` с explicit `attach`, если тема совпадает.
- Exact active title остаётся deterministic attach. Для действительно отдельной темы агент должен
  задать однозначно отличающиеся title и purpose.

## Retrieval без фонового LLM

- Turn-time retrieval остаётся локальным: русский morphology FTS, simple FTS и pinned
  `intfloat/multilingual-e5-small` embeddings в pgvector.
- Один query embedding используется и для обычного claim RAG, и для активации нитей. Нить попадает в
  контекст по найденному member claim, semantic title match или reviewed application skill hint.
- Активная нить собирается детерминированно из whole source-backed records. LLM-generated briefs и
  provider cache удалены; unresolved conflict metadata не теряется в проекции.
- Каждый SQL read применяет live scope authorization, а перед content-bearing DTO выполняется
  финальная проверка актуального доступа.

## Удалённый background pipeline

- Удалены semantic extractor, structured memory output route, relation classifier, thread classifier,
  automatic thread discovery, consolidation worker, extraction candidate processor, approval queue и
  LLM brief jobs/runtime.
- Удалён отдельный `memoryStructuredModel`; основной Eve model больше не имеет скрытого memory model
  route после каждого сообщения.
- Migration `059_main_agent_owned_memory.sql` отключает extraction triggers и retention holds,
  terminally завершает pending/leased legacy workflows, стирает временный plaintext и сохраняет все
  committed claims, evidence, profiles, projects, outcomes, threads и entries.
- Historical workflow tables остаются для persisted audit и migration safety, но runtime writers и
  repository facades для создания новых rows удалены.

## Retired worker и deployment boundary

- `memory-extraction-worker` временно сохранён только из-за schema-v1 production controller service
  contract. Его entrypoint является idle no-op без database, embedding и model calls.
- No-op worker теперь запускается с `network_mode: none`, без environment, secrets и mounts.
- Production deploy останавливает старый provider-capable worker до migration `059`, исключая гонку
  legacy writes во время architecture cutover.
- Root-owned deployment validator обновлён под новый exact Compose security surface. Перед owner
  approval canonical controller modules `release.sh` и `backup.sh` должны быть установлены по
  двухфазной процедуре из production runbook.

## Production deployment

- Release публикуется только из canonical `main` через GitHub Actions с immutable GHCR digests,
  attestations и exact `compose.production.yaml` hash.
- После публикации требуется отдельная owner approval в привязанном личном Telegram-чате.
- Server не собирает images локально и применяет migration только внутри released migrate container.
